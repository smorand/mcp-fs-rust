# US-0101: characterize the db family and the tantivy index before any upgrade

> Spec: SPEC-0055 (sdlc/specs/SPEC-0055-datafusion-and-zstd-upgrade/)
> Nature: DEBT
> Priority: P1
> Depends on: main
> min_tier: 2
> Files touched: 4

## Objective
Write the characterization tests of the db family (DT-001 to DT-011), the tantivy 0.26 index fixture test (DT-030) and the two zstd guards (DT-040, DT-041) on the CURRENT dependency versions, with the literal expected values written into the test source. They are the oracle for the three stories that follow. No production code and no dependency changes.

## Requirements covered
- SPEC-0055/DR-009: The system SHALL produce, for every input covered by the existing test suite and by the characterization tests DT-001 to DT-011, byte identical observable output before and after this change, including the column type names `db.schema` reports.
- SPEC-0055/DR-010: The search family SHALL open a tantivy index directory written by tantivy 0.26 and answer the same query with the same top result.

## Independent Test
`cargo test -p mcp-fs-core --lib tools::db` and `cargo test -p mcp-fs-core --lib search::bm25_sqlite` are green on the unchanged lockfile; `rg -n 'datafusion|tantivy' Cargo.lock | head` still shows datafusion 43 and tantivy 0.26 (no dependency moved).

## Design excerpt
### Decisions
- DEC-006 (SPEC-0055): The characterization tests are written first, recorded on datafusion 43, and become the oracle: where datafusion 55 differs, the code restores the old output; a test expectation is never edited. A difference that cannot be restored is an F finding for the user (a declared break). **Alternatives considered:** accepting new outputs (rejected: smuggles behaviour change into a DEBT). **Implemented by:** DR-009. **Evidence:** `crates/core/src/tools/db.rs:585-703` (8 tests, thin).
- DEC-008 (SPEC-0055): Security tests are structural plus a rejection guard because the effect of the class (uninitialized or freed memory exposure) is not observable by an assertion. The observable instrumentation is DR-004 and DR-012. **Alternatives considered:** a fuzzing harness (rejected: out of proportion for a dependency bump). **Implemented by:** DR-004, DR-012. **Evidence:** advisories text (`cargo audit` output).

### Data model
No schema change. The only persisted data concerned is the tantivy search index directory, which must stay readable (DR-010).

### Contracts
All internal; the `db.*` and `search.*` tool contracts are invariant (DR-009, DR-010). Versions in force after this story chain: datafusion git revision `6f1436fe1407495019d8afec8a9f55663f418d9a`, arrow `60`, parquet `60`, tantivy `0.27`, zstd 0.14.3, zstd-safe 8.2.0, zstd-sys 2.1.2.

### SPEC-0055/DT-030: tantivy 0.26 index still opens
- Level / Driver / Location: integration / direct call to the search backend / `crates/core/src/search/bm25_sqlite.rs` tests module and search e2e
- **Validates:** DR-010, DR-011 on the persisted search index
- The test copies `fixtures/tantivy_0_26/` into `{tempdir}/vol/` (the layout `{tantivy_dir}/{volume_id}/` of `crates/core/src/search/bm25_sqlite.rs:65-79`) and builds the backend with `TantivyBm25Backend::new(tempdir)`; it never opens the fixture in place, since opening for write would modify it.
- Given a small index directory written by tantivy 0.26 with documents `alpha.md` ("hello world") and `beta.md` ("goodbye moon"), committed as a fixture before the upgrade, When the search family opens it under tantivy 0.27 and queries `hello`, Then the top result is `alpha.md` with the same score ordering as recorded on 0.26, And the query `moon` returns `beta.md`.
- **Location:** tests module of `crates/core/src/search/bm25_sqlite.rs`, fixture under `crates/core/src/search/fixtures/tantivy_0_26/`.

### SPEC-0055/DT-040: zstd compressed parquet is read
- Level / Driver / Location: functional e2e / direct call through the registered tools / `crates/core/src/tools/db.rs` tests module
- **Covers:** DR-001, sweep occurrence `Cargo.lock:6887` (datafusion and parquet path)
- **Driver:** direct call through `db.query`
- **Red before the fix because:** EFFECT NOT OBSERVABLE: the class corrupts or exposes memory inside the decoder and no assertion reads it; the observable instrumentation is DT-020 (lockfile) and DT-021 (audit), which are red on main now: `cargo audit` reports 3 vulnerabilities and `deny_toml_drops_the_fixed_git2_ignores` fails.
- The fixture is written by the test with `parquet::file::properties::WriterProperties` using `Compression::ZSTD`, not through `db.convert`.
- Given a Parquet file whose pages are zstd compressed with the rows (1, `Alice`) and (2, `Bob`), When `db.query` runs `SELECT id, name FROM t ORDER BY id`, Then the rows come back exactly, And the same query run a second time returns the same bytes.

### SPEC-0055/DT-041: truncated legacy zstd frame is rejected
- Level / Driver / Location: functional e2e / direct call through the registered tools / `crates/core/src/tools/db.rs` tests module
- **Covers:** DR-004, sweep occurrence `Cargo.lock:6896` (advisory on a failing streaming decompression of a legacy frame)
- **Driver:** direct call through `db.query`
- **Red before the fix because:** EFFECT NOT OBSERVABLE: as DT-040; the rejection is the expected behaviour on both versions, so this test is a guard, not the proof.
- The fixture is the file of DT-040 with the bytes of the first data page replaced in place, the page header and the file length unchanged.
- Given a Parquet file whose first data page is replaced by the literal bytes `22 B5 2F FD 00 00` (a legacy zstd magic number followed by a truncated header), When `db.query` runs `SELECT * FROM t`, Then the call returns an error and no rows, And a following `db.query` on the valid file of DT-040 returns its rows unchanged.
