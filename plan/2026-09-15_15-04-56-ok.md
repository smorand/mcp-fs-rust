# PostgreSQL and SQL Server as relational backends

> Generated: 2026-09-15 15:04
> Request: add PostgreSQL and SQL Server support as a configurable backend instead of SQLite, driven by the mandatory YAML config file

## Summary

Today every piece of server state lives in SQLite: per-volume metadata trees, the ACL
registry, the per-project git index and the OAuth token store. Four call sites open a
`SqliteDb` directly and roughly 45 hand-written SQL statements assume SQLite dialect and
`?N` positional parameters. This plan introduces a dialect-aware relational layer so
`infra.meta.backend`, `infra.admin.backend` and the new `infra.git`/`infra.oauth` sections
accept `sqlite`, `postgres` or `sqlserver`, selected purely from the YAML file.

The C# parity constraint is formally retired (per decision Q2), which unblocks the two
schema changes portability requires: a `volume_id` discriminator column so one Postgres or
SQL Server database can host many volumes, and `BYTEA`/`VARBINARY` typing for the OAuth
token blob. Config resolution gains a documented CLI > ENV > file precedence including
`~/.config/mcp-fs/config.yaml`.

## Scope

**In scope**
- A `RelationalDb` abstraction with three dialect implementations (SQLite, PostgreSQL, SQL Server).
- Porting all four SQLite consumers onto it: `storage/meta.rs`, `storage/admin.rs`,
  `git/db.rs`, `git/oauth/persistence.rs`.
- New/extended config sections: `infra.meta`, `infra.admin`, `infra.git`, `infra.oauth`,
  each with `backend`, `dsn`, and pool settings; secrets via `${VAR}` only.
- Schema migration to a `volume_id`-discriminated multi-tenant layout for the server backends.
- Config resolution: `--config` > `$MCP_FS_CONFIG` > `~/.config/mcp-fs/config.yaml` >
  `${MCP_FS_CONFIG_DIR:-config}/${MCP_FS_CONFIG_NAME:-local}.yaml`, documented.
- Docker-compose based integration tests for both new engines, opt-in like the MinIO tests.
- Retire the parity harness from CI gating and document the lifecycle split.

**Out of scope**
- The `sqlite.*` MCP tool family (`tools/sqlite.rs`) and the `db.*` DataFusion family. These
  operate on `.db` **files inside a volume** and are a different concern entirely; they stay
  SQLite/DataFusion. A `postgres.*` tool family for querying remote user databases is a
  separate future request, explicitly not this one.
- The blob store. Bytes stay in `local`/`s3`; no blobs move into the relational database.
- The `git/repo.rs` libgit2 working directory, which remains a real filesystem path.
- Cross-engine online migration tooling (an offline export/import command is included; live
  replication is not).

## Approach

**Chosen: a narrow `RelationalDb` trait over `sqlx::Pool<Postgres>` / `Pool<Sqlite>` plus
`tiberius` for SQL Server, with per-dialect SQL emitted through a small `Dialect` helper.**

The decisive constraint, verified against crates.io during planning: **sqlx removed its
MSSQL driver in 0.7 and the rewrite has not shipped** (sqlx 0.9.0, current). So the tempting
"just use `sqlx::Any` for all three" approach is not available for SQL Server at all. The
realistic SQL Server options are `tiberius` 0.12.3 (last release 2024-07-19, effectively
unmaintained, ships known-unpatched advisories) and the community fork `tiberius-ng` 0.13.1
(released 2026-08-30, actively maintained, but only ~3.5k downloads). We take
**`tiberius-ng`**, pinned, behind a `sqlserver` cargo feature that is **off by default**, so
a default build carries neither the dependency nor its risk. This is recorded as a known
risk below rather than hidden.

Alternatives considered:

- **`sqlx::Any` for everything.** Cleanest single abstraction, and it genuinely handles
  SQLite + Postgres. Rejected: no MSSQL driver exists, so SQL Server would be unreachable,
  which is half the request. `Any` also erases compile-time query checking and still leaks
  dialect differences in DDL, so it buys less than it appears to.
- **Keep raw drivers per backend, duplicate each query three times.** Rejected: ~45
  statements times 3 engines is 135 hand-maintained strings, and the four consumers would
  drift apart. The trait keeps one query per operation with dialect-parameterized rendering.
- **An ORM (SeaORM / Diesel).** SeaORM supports Postgres/SQLite but not MSSQL either, and
  both would force a rewrite of every store plus fight the existing hand-tuned recursive
  path queries. Rejected as a large rewrite that still does not solve SQL Server.
- **ODBC for SQL Server.** Genuinely portable and well-maintained (`odbc-api`), but requires
  a system driver manager and a C toolchain on every host, which contradicts the current
  zero-external-dependency `bundled` SQLite posture. Rejected as a deployment tax; noted as
  the fallback if `tiberius-ng` proves unhealthy.

**Why the schema must change (and why that is now allowed).** SQLite gets one *file* per
volume (`state/volumes/{project_id}.db`), so the `nodes` table needs no tenant column. A
Postgres or SQL Server deployment cannot sanely create one *database* per project on the
fly. So the ported schema adds `volume_id` to `nodes` and `blob_refs`, and to the three
`git_*` tables, with `PRIMARY KEY (volume_id, path)`. Under the SQLite backend `volume_id`
is still written but is constant per file, so a SQLite deployment keeps one file per volume
and behaves exactly as today. This divergence is only acceptable because parity is retired;
it is the single change that makes multi-tenant SQL viable.

**Transaction semantics are preserved, and the concurrency model improves.** Today
`SqliteDb` serializes *everything* behind one mutex on one connection. That is correct but
is a hard throughput ceiling. Postgres and SQL Server get a real connection pool with
per-request transactions; SQLite keeps the existing serialized single connection, since WAL
plus one writer is what makes it safe. Callers see the same `run(|tx| ...)` shape either way,
so no business logic changes.

## Changes

### New: `crates/mcp-fs/src/storage/rel/` (the relational layer)

- `mod.rs` — `RelationalDb` trait, the async surface every store uses:
  ```rust
  #[async_trait]
  pub trait RelationalDb: Send + Sync {
      fn dialect(&self) -> Dialect;
      async fn execute(&self, q: &Query) -> Result<u64>;
      async fn query(&self, q: &Query) -> Result<Vec<RowValues>>;
      async fn query_opt(&self, q: &Query) -> Result<Option<RowValues>>;
      /// Run a closure inside one transaction, retried on serialization failure.
      async fn transaction<'a>(&'a self, f: TxFn<'a>) -> Result<()>;
      async fn migrate(&self, schema: &SchemaSet) -> Result<()>;
  }
  ```
  `Query` carries SQL text plus typed `Vec<SqlValue>` params. `RowValues` is an index/name
  addressable row so the existing `read_row`-style mappers port with minimal edits.
  **Public API change**: this trait is new public surface in the `storage` module.
- `dialect.rs` — `enum Dialect { Sqlite, Postgres, SqlServer }` plus the three things that
  actually differ:
  - **placeholders**: `?1` / `$1` / `@P1`, rendered from a single canonical form;
  - **upsert**: `INSERT .. ON CONFLICT .. DO UPDATE` (SQLite/PG) vs `MERGE` (SQL Server),
    replacing today's `INSERT OR IGNORE` / `INSERT OR REPLACE`;
  - **types**: `INTEGER/REAL/TEXT/BLOB` vs `BIGINT/DOUBLE PRECISION/TEXT/BYTEA` vs
    `BIGINT/FLOAT/NVARCHAR(MAX)/VARBINARY(MAX)`.
- `sqlite.rs` — wraps the existing `SqliteDb` (kept, not deleted) behind the trait.
- `postgres.rs` — `sqlx::PgPool`, `#[cfg(feature = "postgres")]`.
- `sqlserver.rs` — `tiberius-ng` + `bb8` pool, `#[cfg(feature = "sqlserver")]`.
- `schema.rs` — `SchemaSet`: table/column/index/PK declarations rendered per dialect, so
  the four schemas are declared once instead of as three DDL string literals each.

### Modified stores (behavior preserved, storage generalized)

- `storage/meta.rs` — `SqliteMetaStore` becomes `RelationalMetaStore` holding
  `Arc<dyn RelationalDb>` plus its `volume_id`. `MetaBackend` trait is **unchanged**, so
  `core/fs_ops.rs` and every tool are untouched. Two SQL details need care:
  - `subtree` / `remove_subtree` / `rename` use `path LIKE '{prefix}/%'` with an
    **unescaped** prefix. A project id or path containing `%` or `_` currently
    over-matches; on Postgres this is the same bug and on SQL Server `[` also matters. The
    port adds `ESCAPE '\'` with proper escaping, fixing a latent bug rather than porting it.
  - `ORDER BY length(path)` in `rename` becomes dialect-rendered (`LEN` on SQL Server).
- `storage/admin.rs` — same treatment. Keeps the caseless-identity behavior and the
  `role<>'owner'` guard on `remove_member`. The `ON DELETE CASCADE` foreign key is declared
  through `SchemaSet` (SQLite needs `PRAGMA foreign_keys=ON`, already set; Postgres and SQL
  Server enforce it natively).
- `git/db.rs` — `SqliteGitDb` becomes `RelationalGitDb`. Its `INSERT OR REPLACE` upserts
  become dialect upserts. The test asserting table names via `sqlite_master` moves to a
  dialect-aware introspection helper.
- `git/oauth/persistence.rs` — `token_enc BLOB` becomes dialect binary. Encryption is
  unchanged (AES-256-GCM, `MCPFS_TOKEN_KEY`); the ciphertext is simply stored as `BYTEA` /
  `VARBINARY(MAX)`. Its methods stay synchronous-looking to callers via `block_in_place`-free
  async wrappers, since Postgres/SQL Server clients are async-only. **This is an internal
  signature change** in `SqliteOAuthPersistence`'s two callers in `git/oauth/store.rs`.

### Factories and lifecycle

- `storage/mod.rs` — `build_meta_store` / `build_admin_store` gain `postgres` and
  `sqlserver` branches; the error message enumerates the now-valid values. Pools are built
  **once** at startup and shared, not per project, so add `RelationalPools` to shared state.
- `git/repo.rs:170` currently calls `SqliteGitDb::open(&db_path)` directly, bypassing any
  factory. It gains a `build_git_db(&config, project_id)` factory call, matching the others.
- `storage/mod.rs::teardown_volume` deletes `.db`/`-wal`/`-shm` files. For the SQL backends
  teardown becomes `DELETE FROM ... WHERE volume_id = $1` across the volume's tables inside
  one transaction. The file-deletion path stays for SQLite.
- `app.rs` — builds the pools, runs `migrate()` for each configured backend, and fails boot
  loudly on an unreachable database (a wrong DSN must not surface later as a per-request 500).

### Config (`config.rs`) — new keys

```yaml
infra:
  meta:
    backend: sqlite            # sqlite | postgres | sqlserver
    dir: state/volumes         # sqlite only
    dsn: "${MCPFS_META_DSN}"   # postgres/sqlserver only, secret
    schema: mcpfs              # postgres only, default "public"
    pool: { max_connections: 10, acquire_timeout_secs: 30 }
  admin:
    backend: sqlite
    path: state/admin.db
    dsn: "${MCPFS_ADMIN_DSN}"
    pool: { ... }
  git:                          # NEW section; was hardcoded to state/git/{p}.db
    backend: sqlite
    dsn: "${MCPFS_GIT_DSN}"
  oauth:                        # NEW section; was hardcoded to state/oauth.db
    backend: sqlite
    dsn: "${MCPFS_OAUTH_DSN}"
```
Defaults keep every existing deployment working unchanged: absent section means `sqlite`
with today's paths. A DSN is **only** read from `${VAR}` expansion in practice and is
redacted in `Debug` and in every log line and error message, like the OAuth tokens already
are. Validation is at load time: `backend: postgres` with an empty `dsn` is
`ERR_INVALID_ARGUMENT` at boot.

Two new config validation rules, because silent misconfiguration is the real risk here:
`backend: postgres` without the `postgres` cargo feature compiled is a clear boot error
naming the missing feature; and a `dsn` set while `backend: sqlite` is a boot error rather
than being silently ignored.

### CLI and config resolution (`cli.rs`)

Documented precedence, highest first:
1. `--config PATH` (`-c`)
2. `$MCP_FS_CONFIG`
3. `~/.config/mcp-fs/config.yaml` (respects `$XDG_CONFIG_HOME` when set) — **new**
4. `${MCP_FS_CONFIG_DIR:-config}/${MCP_FS_CONFIG_NAME:-local}.yaml`

Step 3 is new and applies only when the file exists, so it cannot break a CWD-relative
setup. The config file stays mandatory: if no candidate resolves, boot fails with
`ERR_INVALID_ARGUMENT` listing every path tried, which is friendlier than today's
single-path message. `resolve_config_path_with` keeps its injectable-env shape so this stays
unit-testable without touching the process environment; it gains an injectable
"does this path exist" probe for the same reason.

New CLI verb `mcp-fs migrate --from <config> --to <config>` for the offline cross-engine
move: reads every volume through the source backends and writes it through the destination,
verifying row counts and blob shas. Without this, "switch to Postgres" means abandoning
existing data, which is not an acceptable deliverable.

### Dependencies (`Cargo.toml`)

```toml
sqlx = { version = "0.9", default-features = false, features = [
  "runtime-tokio", "tls-rustls", "postgres", "macros" ] }   # optional
```

Cargo features: `postgres`, `sqlserver`, and `all-backends`. Neither is in `default`.
`rusqlite` with `bundled` stays exactly as is.

## Assumptions and defaults

Labeled assumptions, taken instead of another question round because each is low risk and
reversible:

1. **SQLite stays the default backend** and every existing config keeps working untouched.
   A Postgres/SQL Server deployment is opt-in.
2. **Separate DSNs per concern** (meta/admin/git/oauth) rather than one global DSN. Pointing
   all four at the same DSN is supported and expected to be the common case; tables do not
   collide because names are distinct.
3. **One Postgres/SQL Server database hosts all volumes**, discriminated by `volume_id`.
   Per-project databases are not attempted.
4. **`postgres` and `sqlserver` are non-default cargo features.** A default build is
   byte-for-byte as today, with no new dependency surface.
5. **The `sqlite.*` and `db.*` MCP tool families are untouched.** Confirmed out of scope.
6. **PostgreSQL 14+ and SQL Server 2019+** are the floors, both current supported releases.
7. **No online migration.** The `migrate` verb is offline, run with the server stopped.

## Test plan / verification

Success criteria: identical observable behavior across all three backends, proven by running
one shared suite against each.

1. **Backend-parametric conformance suite** (the core of this work). The existing
   `MetaBackend` / `AdminBackend` tests are lifted into a `backend_conformance` module
   parameterized over a backend factory, then run against SQLite (in-memory), Postgres and
   SQL Server. Same assertions, three engines. This is what proves the port.
2. **Dialect unit tests** with no database: placeholder rendering (`?1`/`$1`/`@P1`), upsert
   rendering, DDL type mapping, and `LIKE` escaping for `%`, `_` and `[`.
3. **Specific regression cases**, chosen because they are where this port can silently break:
   - a path containing `%` and `_` must not over-match in `subtree`/`remove_subtree`/`rename`
     (currently buggy, must pass on all three after the fix);
   - `rename` of a deep tree preserves order (`length(path)` vs `LEN(path)`);
   - refcount GC: two volumes referencing the same sha must not GC each other's blob, which
     `volume_id` makes newly possible to get wrong;
   - `remove_member` still refuses to remove an owner;
   - `delete_project` still cascades members on all three engines;
   - concurrent writers to one volume: 25 parallel writes, no lost update, no deadlock
     (Postgres and SQL Server can genuinely deadlock where the SQLite mutex could not, so
     transaction retry is exercised here);
   - OAuth round trip: encrypt, store as `BYTEA`/`VARBINARY`, restart, decrypt.
4. **Config tests**: precedence order including the XDG step; `backend: postgres` with empty
   `dsn` fails at boot; DSN never appears in `Debug` output or logs (assert on captured
   output, since a leaked password is the worst failure mode here).
5. **Migration test**: build a volume on SQLite, `mcp-fs migrate` to Postgres, assert tree,
   sizes, shas and ACLs match, then run the same fs operations against both and diff.
6. **Integration harness**: `docker-compose.test.yml` with `postgres:16` and
   `mssql/server:2022`, opt-in via `MCPFS_TEST_PG_DSN` / `MCPFS_TEST_MSSQL_DSN`, skipped when
   unset so `cargo test --workspace` stays green with no Docker.
7. **Gate**: `cargo test --workspace` and `cargo clippy --all-targets --all-features -D warnings`
   both clean. `--all-features` matters now that features exist.

Verification commands:
```
cargo test --workspace                                   # SQLite only, no Docker needed
docker compose -f docker-compose.test.yml up -d
MCPFS_TEST_PG_DSN=... MCPFS_TEST_MSSQL_DSN=... \
  cargo test --workspace --all-features -- --include-ignored
cargo clippy --all-targets --all-features -- -D warnings
```

## Open risks

1. **`tiberius-ng` is a young fork** (0.13.1, ~3.5k downloads, single maintainer) and the
   original `tiberius` is unmaintained with open advisories. This is the weakest link in the
   plan. Mitigation: `sqlserver` is a non-default feature, the driver sits behind
   `RelationalDb` so swapping to `odbc-api` touches one file, and the pin is explicit.
   **Severity: medium.** Worth a conscious accept before starting.
2. **Retiring parity removes a safety net.** The differential harness currently catches
   regressions the unit tests do not. The backend-parametric conformance suite replaces it
   for storage, but the harness also covered tool-level shapes. Recommendation: keep the
   harness runnable and green against SQLite for one more release rather than deleting it.
3. **`volume_id` is a real divergence.** SQLite volumes written by the new code carry a
   column the old code does not know about. SQLite tolerates the extra column on read, but a
   downgrade is not clean. The `migrate` verb covers the forward path; there is no automated
   downgrade.
4. **Transaction retry is new behavior.** Postgres serialization failures and SQL Server
   deadlock victims must be retried, which SQLite's mutex made impossible. A retry must be
   safe to re-run, so any non-idempotent closure is a latent bug. Every `transaction` closure
   needs review for idempotence; the concurrency test targets this but cannot prove absence.
5. **Latency and failure modes change shape.** SQLite is an in-process call that cannot time
   out; a remote database can be slow, drop mid-transaction, or exhaust the pool. Error
   mapping needs a deliberate pass so a pool timeout is not reported as
   `ERR_INTERNAL: sqlite: ...`. A new `ERR_UNAVAILABLE`-style mapping may be warranted.
6. **Estimated size is substantial**: 4 stores, ~45 statements, 2 new drivers, a migration
   verb and a tripled test matrix. Suggested sequencing, each step independently shippable
   and green: (1) `RelationalDb` + dialect + SQLite adapter behind it, no behavior change;
   (2) conformance suite extracted; (3) Postgres; (4) config plus resolution plus docs;
   (5) SQL Server; (6) `migrate` verb.
7. **`git/repo.rs` still needs a real filesystem path** for libgit2's working directory even
   when the git *index* lives in Postgres. So a fully stateless-disk deployment is not
   achieved by this plan; `state/git-repos/` remains. Worth stating plainly so nobody expects
   otherwise.
