# Search: BM25 + RAG + Reranking

> Generated: 2026-09-16 (amended after design discussion)
> Request: Ajouter le support Search comprenant RAG + BM25 avec les cas: BM25 only, RAG only (config modèle + stockage PostgreSQL pg_vector) avec ou sans reranking, et Both avec reranking sur double recherche.

## Summary

A new `search.*` tool family (4 tools: `search.index`, `search.query`, `search.delete`,
`search.status`) is added as an optional feature, mirroring the pattern of `web.*`,
`context7.*`, and `db.*`. BM25 and vector search are implemented differently per relational
backend: on PostgreSQL, both use native server-side storage (`tsvector`/GIN for BM25,
`pgvector` for vectors), keeping the server fully stateless and replica-safe. On SQLite
(dev/single-instance posture), BM25 uses an on-disk Tantivy index and vectors use the
`sqlite-vec` extension (statically linked C, same zero-external-dependency posture as
`rusqlite`). Reranking calls a configurable HTTP endpoint. The existing relational
compatibility layer (`RelationalDb` / `Dialect` / `SchemaSet`) is extended, not bypassed.

## Scope

In scope:
- 4 MCP tools: `search.index`, `search.query`, `search.delete`, `search.status`
- BM25 on PostgreSQL via `tsvector` + GIN + `ts_rank_cd`
- BM25 on SQLite via Tantivy (on-disk, dev posture, rebuildable)
- Vector search on PostgreSQL via `pgvector` (`VECTOR(n)` column, IVFFlat index)
- Vector search on SQLite via `sqlite-vec` (`vec0` virtual table, statically linked)
- Configurable OpenAI-compatible embedding HTTP endpoint
- Optional configurable reranker HTTP endpoint (Cohere/Jina shape)
- Three query modes: `bm25`, `rag`, `both` (with RRF fusion + optional reranking)
- New `search` config section in `ServerConfig`
- New cargo features: `rag` (pgvector + sqlite-vec), all-backends includes `rag`
- Dialect layer extended: `ColumnType::Tsvector`, `ColumnType::Vector(u32)`,
  `IndexType::Gin`, `IndexType::IvfFlat`
- TOOL_CONTRACT.txt and golden JSON updated
- `config/local.yaml` updated with commented `search:` block
- `.agent_docs/search.md` created
- Unit tests (testkit pattern) + golden contract test
- Stub HTTP server for embedding tests (`scripts/search_embedding_fake.py`)

Out of scope:
- Automatic re-indexing on `fs.write` / `fs.edit` (explicit `search.index` call only)
- SQL Server vector support (no native vector type; documented as unsupported)
- `search.*` on the REST data plane `/api/fs` (MCP surface only)
- Streaming results
- Multi-modal (image) embeddings
- Chunking strategies beyond a fixed character window

## Approach

### BM25 storage per backend

**PostgreSQL (stateless, replica-safe):** A `search_fts` table with a `tsvector` column
and a GIN index. Indexing calls `to_tsvector('english', ...)`, querying uses
`to_tsquery` + `ts_rank_cd`. No extra crate. Fully transactional, replicated alongside
the rest of the relational state. Ranking is `ts_rank_cd`, which approximates BM25 well
enough for project-sized corpora (the gap vs Tantivy is real but not the deciding factor
here; statelessness is).

**SQLite (on-disk, dev posture):** Tantivy index under `state/search/{project_id}/`.
Accepted with a clear caveat: the index is ephemeral local state. On pod restart or
volume remount the index is gone and must be rebuilt via `search.index`. The
`search.status` tool reports whether the index is warm. This is the right trade-off for
a SQLite deployment, which is already a single-instance posture by design (the
`storage/sqlite.rs` serialized single connection makes that explicit).

Alternative considered: SQLite FTS5. Rejected: it would embed the search index inside
the metadata database, coupling its lifecycle to the metadata schema migration. Tantivy
as a separate directory is cleaner to reason about and trivially disposable.

### Vector storage per backend

**PostgreSQL:** `pgvector` extension. New `search_chunks` table with a `VECTOR(n)`
column. The `rag` cargo feature gates this; it implies `postgres`. `CREATE EXTENSION IF
NOT EXISTS vector` runs in the pool's `after_connect` hook alongside the schema setup.
IVFFlat index on the embedding column (exact cosine scan is the default until corpus
exceeds ~10k chunks; IVFFlat is created unconditionally so it becomes effective at
scale without a migration).

**SQLite:** `sqlite-vec` crate (`asg017/sqlite-vec` v0.1.9). The crate embeds the C
source and statically links at build time via the `cc` crate — same posture as
`rusqlite` with `bundled`. No system library, no `apt install`. Vectors are stored in a
`vec0` virtual table (`CREATE VIRTUAL TABLE search_vec USING vec0(embedding float[N])`);
metadata (path, chunk_idx, chunk_text) lives in a companion regular table joined by
rowid. The extension is registered via `sqlite3_auto_extension` at connection open in
`storage/sqlite.rs` when the `rag` feature is on.

**SQL Server:** `ERR_NOT_SUPPORTED` at runtime for both BM25 and RAG. Documented.
The schema tables are still declared (with `TEXT` fallbacks for the vector column) so
the DDL applies cleanly; the tools simply reject the call.

### Compatibility layer extension

The existing `RelationalDb` / `Dialect` / `SchemaSet` machinery is extended, not
bypassed:

- `dialect.rs`: `ColumnType::Tsvector` (renders as `TSVECTOR` on PostgreSQL, `TEXT` on
  others), `ColumnType::Vector(u32)` (renders as `VECTOR(n)` on PostgreSQL, `TEXT` on
  SQLite/SQL Server — the actual SQLite vector storage uses the `vec0` virtual table
  alongside it, not this column).
- `schema.rs`: `IndexType::Gin` (renders as `USING GIN` on PostgreSQL, standard `CREATE
  INDEX` on others), `IndexType::IvfFlat` (PostgreSQL-only; skipped on other dialects).
- The `vec0` virtual table DDL cannot fit the standard `SchemaSet::render_table` path
  (it is `CREATE VIRTUAL TABLE ... USING vec0(...)`, not a column list). A new
  `SchemaSet::virtual_tables: Vec<VirtualTable>` field handles this; `render()` emits
  virtual table DDL after regular tables, skipped on non-SQLite dialects. The compiler
  finds every render site via the exhaustive `match` on `Dialect`.

### Query mode dispatch

| `mode` | BM25 engine | Vector engine | Merge | Reranking |
|--------|-------------|---------------|-------|-----------|
| `bm25` | tsvector or Tantivy | — | — | No |
| `rag` | — | pgvector or sqlite-vec | — | Optional |
| `both` | tsvector or Tantivy | pgvector or sqlite-vec | RRF | Optional |

The `mode` param on `search.query` overrides the server config default per call.
Requesting a mode that requires a capability not provisioned (e.g. `rag` with no
embedding config, or `rag` on SQL Server) returns `ERR_NOT_SUPPORTED` with a message
naming the missing prerequisite.

### Public API (tool contract additions)

```
search.index
  desc: Index a file or directory into the search engine for this volume.
  params: mount_id:string, path:string, recursive:boolean=false,
          chunk_size:integer=1000, chunk_overlap:integer=100
  required: ['mount_id', 'path']
  returns: {"indexed": 12, "skipped": 0, "path": "/docs"}

search.query
  desc: Search indexed content. mode overrides the server default (bm25, rag, both).
  params: mount_id:string, query:string, mode:string=null,
          top_k:integer=10, rerank:boolean=true
  required: ['mount_id', 'query']
  returns: {"results": [{"path": "/doc.md", "score": 0.91, "chunk": "...", "rank": 1}],
            "mode_used": "both"}

search.delete
  desc: Remove a path from the search index.
  params: mount_id:string, path:string, recursive:boolean=false
  required: ['mount_id', 'path']
  returns: {"deleted": 5}

search.status
  desc: Report index statistics for this volume.
  params: mount_id:string
  required: ['mount_id']
  returns: {"bm25_docs": 42, "vector_chunks": 210, "mode": "both", "bm25_warm": true}
```

### New relational table: `search_fts` (PostgreSQL BM25)

```sql
CREATE TABLE IF NOT EXISTS search_fts (
  volume_id   TEXT     NOT NULL,
  path        TEXT     NOT NULL,
  chunk_idx   INTEGER  NOT NULL,
  chunk_text  TEXT     NOT NULL,
  tsv         TSVECTOR NOT NULL,
  PRIMARY KEY (volume_id, path, chunk_idx)
);
CREATE INDEX IF NOT EXISTS idx_search_fts_tsv ON search_fts USING GIN (tsv);
```

### New relational table: `search_chunks` (pgvector, PostgreSQL)

```sql
CREATE TABLE IF NOT EXISTS search_chunks (
  volume_id   TEXT         NOT NULL,
  path        TEXT         NOT NULL,
  chunk_idx   INTEGER      NOT NULL,
  chunk_text  TEXT         NOT NULL,
  embedding   VECTOR(N)    NOT NULL,   -- N from search.embedding.dimensions
  PRIMARY KEY (volume_id, path, chunk_idx)
);
CREATE INDEX IF NOT EXISTS idx_search_chunks_emb
  ON search_chunks USING ivfflat (embedding vector_cosine_ops);
```

### New SQLite structures (Tantivy + sqlite-vec)

Tantivy: one index directory per volume at `state/search/{project_id}/`. Schema:
fields `path` (TEXT, stored), `chunk_idx` (u64, stored), `chunk_text` (TEXT, indexed +
stored). Opened lazily on first `search.index` call, reused across requests behind an
`Arc<RwLock<Index>>` in the SQLite search backend.

sqlite-vec: two tables per volume (created in the existing per-volume SQLite database):

```sql
-- regular companion table
CREATE TABLE IF NOT EXISTS search_vec_meta (
  rowid      INTEGER PRIMARY KEY,
  volume_id  TEXT    NOT NULL,
  path       TEXT    NOT NULL,
  chunk_idx  INTEGER NOT NULL,
  chunk_text TEXT    NOT NULL
);
-- vec0 virtual table (DDL outside SchemaSet::render_table, emitted via VirtualTable)
CREATE VIRTUAL TABLE IF NOT EXISTS search_vec
  USING vec0(embedding float[N]);
```

KNN query: `SELECT m.path, m.chunk_text, v.distance FROM search_vec v JOIN search_vec_meta m ON m.rowid = v.rowid WHERE v.embedding MATCH ? AND k = ?`.

### Config section (new, `ServerConfig.search`)

```yaml
search:
  enabled: false
  mode: bm25               # bm25 | rag | both
  tantivy_dir: state/search  # SQLite only; ignored on PostgreSQL

  embedding:
    endpoint: ""           # OpenAI-compatible /v1/embeddings URL
    model: ""              # e.g. text-embedding-3-small
    api_key_env: ""        # env var name holding the key
    dimensions: 1536       # must match model output; frozen after first index call

  reranking:
    enabled: false
    endpoint: ""           # Cohere/Jina rerank URL
    model: ""
    api_key_env: ""
    top_n: 10              # how many to send to the reranker
```

### New cargo feature

```toml
# rag gates both pgvector (PostgreSQL) and sqlite-vec (SQLite).
# It implies postgres so --features rag alone is sufficient for a PostgreSQL+vector build.
rag = ["postgres", "dep:sqlite-vec"]
all-backends = ["postgres", "sqlserver", "rag"]
```

Tantivy is NOT behind a feature flag. It is a compile-time dependency whenever
`mcp-fs` is built, but it is only activated at runtime when `search.enabled = true`.
The binary size increase (~3 MB stripped) is accepted.

## Assumptions and defaults

- `sqlite-vec` version `0.1.9` (latest as of 2026-09-16; pre-v1, pinned exactly in
  `Cargo.toml` to prevent surprise API changes).
- `tantivy` version `0.22` (latest stable; will be confirmed at implementation time).
- The embedding endpoint speaks the OpenAI `/v1/embeddings` shape: POST `{model,
  input: [string]}`, response `{data: [{embedding: [float]}]}`. Jina, Cohere, and most
  self-hosted models expose this shape.
- The reranker speaks the Cohere Rerank v1 shape: POST `{model, query, documents:
  [string]}`, response `{results: [{index: int, relevance_score: float}]}`. Jina
  supports the same.
- `search.*` tools require project membership (same `state.authorize` gate as `fs.*`).
- The `tsvector` language is `'english'` by default. A `search.fts_language` config key
  can override this; deferred to a follow-up if needed.
- `search.index` is idempotent: re-indexing a path replaces its existing chunks (DELETE
  WHERE path = ? before INSERT).
- The Tantivy index (SQLite path) is documented as ephemeral. `search.status` reports
  `"bm25_warm": false` when the index directory is absent, hinting the caller to re-index.
- `ColumnType::Vector(u32)` renders as `TEXT` on SQLite (the actual vector storage uses
  the `vec0` virtual table, not this column). On SQL Server it also renders as `TEXT`
  and the search tools return `ERR_NOT_SUPPORTED`.
- RRF constant k = 60 (standard default, not configurable in this iteration).

## Open risks

1. **sqlite-vec is pre-v1.** The `asg017/sqlite-vec` crate states explicitly that
   breaking changes are expected before 1.0. Pinned exactly (`= "0.1.9"`). Blast radius
   is contained to `search/vector_sqlite.rs`. The mitigation is the same as for
   `tiberius-ng`: isolation in one file, pinned version, documented exit.

2. **Tantivy index is ephemeral on SQLite.** Already accepted. `search.status` must
   report `bm25_warm: false` clearly, and `.agent_docs/search.md` must explain
   rebuild procedure. Risk: an LLM calls `search.query` on a cold SQLite instance and
   gets empty results without understanding why. Mitigation: `search.query` returns a
   `warning` field when `bm25_warm: false`.

3. **Embedding dimension freeze.** Once vectors are stored at dimension N, changing
   `search.embedding.dimensions` breaks all stored vectors silently. Boot-time
   validation reads one stored embedding dimension (if any) and rejects a mismatch with
   a clear error naming the fix (delete chunks + re-index). Deferred to implementation;
   called out here so it is not forgotten.

4. **pgvector IVFFlat requires `lists` tuning.** The default `lists = 100` works well
   above ~100k vectors, poorly below ~1k. Exact scan (no index) is used automatically
   below a threshold (`SET enable_indexscan = off` when chunk count < 1000). Documented
   in `.agent_docs/search.md`.

5. **`vec0` virtual table DDL outside `SchemaSet`.** The `VirtualTable` extension to
   `SchemaSet` is new surface in the schema renderer. Every `match` on `Dialect` is
   exhaustive, so a missing case fails to compile, which is the existing safety net.
   Still, this is the first DDL path that cannot be described as a column list, so it
   needs careful review during implementation.

6. **SQL Server search unsupported.** Documented and returns `ERR_NOT_SUPPORTED`. Not
   a risk per se, but worth flagging so no one spends time trying to make it work in
   this iteration.
