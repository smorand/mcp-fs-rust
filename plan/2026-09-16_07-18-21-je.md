# Document as a Service

> Generated: 2026-09-16
> Request: evaluate and specify "document as a service": an external converter (CLI or HTTP API) turning an uploaded document into its Markdown companion, triggered by a flag on upload.

## Summary

Add a `doc_service` configuration section describing an external, stateless
document-to-Markdown converter, in two interchangeable forms: a **CLI** invoked as
`doc-convert --stdout {document}` (Markdown on stdout), or an **HTTP API** called with a
configurable auth header. Add a binary upload tool `fs.write_bytes` (base64) to the MCP
surface, since none exists today, and a `trigger_documentation_service` boolean on every
byte-upload surface (MCP `fs.write_bytes`, REST `/upload` and `/write-bytes`). When the
flag is set, the file is stored AND its Markdown companion is stored beside it at the exact
path `companion_md_path(source)` (`toto.pptx` -> `toto.md`). Only PowerPoint, Word, PDF,
audio and video extensions are eligible. A new tool `fs.documentize` runs the same
conversion on a file already stored in a volume.

The companion path deliberately matches the one `fs.extract_text` already uses, so a
doc-service companion is served as a cache hit by the built-in extractor at no extra cost.

## Scope

**In scope**

- New config section `doc_service` (enabled, mode cli|api, per-mode settings, eligible
  extensions, timeouts, size cap), with `${VAR}` expansion and a redacting secret newtype
  for the API token.
- New module `crates/mcp-fs/src/docs/service.rs`: trait `DocService` + `CliDocService` +
  `ApiDocService` + `NullDocService`, built once at boot and held by `AppState`.
- CLI execution sandboxed to a per-call temporary directory, deleted on every exit path
  (success, error, timeout, kill).
- New engine function in `core/fs_ops.rs`, the single implementation shared by MCP and REST.
- New MCP tools: `fs.write_bytes` (base64 binary write, carries the flag) and
  `fs.documentize` (convert a stored file). Contract golden regenerated.
- New REST route `POST /api/fs/{mount_id}/write-bytes`, plus a
  `trigger_documentation_service` form field on the existing multipart `/upload`, plus
  `POST /api/fs/{mount_id}/documentize`. OpenAPI updated.
- A fake doc-service HTTP server (`scripts/doc_service_fake.py`) wrapping `doc-convert`,
  for functional tests and local dev of the API mode.
- Unit tests (stub service), config tests, contract tests, OpenAPI tests, plus an opt-in
  test that really shells to `doc-convert` and asserts the sandbox stays clean.
- Docs: `AGENTS.md`, `README.md`, `.agent_docs/config.md`, `.agent_docs/tools.md`,
  `.agent_docs/api.md`, `.agent_docs/testing.md`.

**Out of scope**

- Image extraction from documents (slides images, base64 inlining, captions). Whatever the
  converter puts in the Markdown is stored verbatim; we ask for nothing more.
- Asynchronous or queued conversion, progress reporting, retries after a failed conversion.
- Rewiring `fs.extract_text` to delegate to the doc service. The built-in extractor stays
  as it is; the only coupling is the shared companion path.
- Any conversion output other than Markdown on the primary channel.

## Approach

The conversion is an explicit, per-call, **synchronous** side effect of a byte upload.

Alternatives considered:

- *Hook inside `fs_ops::write_bytes` for every eligible extension.* Rejected: it would fire
  on edits and on internally generated files, it has no way to express the user's opt-in
  flag, and it makes every write pay a multi-second latency. The flag exists precisely
  because the caller decides.
- *Background job, upload returns immediately.* Rejected for now: the user stated the
  service is stateless and returns its result on its output. A job queue means persisted
  job state, a status tool, and a failure-reporting surface, all of which is a bigger
  feature than what was asked. The synchronous cost is real (measured: 22 s for a one-page
  PDF via `doc-convert`) and is handled with a generous configurable timeout, documented as
  a known limitation.
- *MCP-side: put the flag on `fs.write` only.* Rejected: `fs.write` is text-only, so it
  could never carry a `.pptx`. The user confirmed a binary write tool is wanted in its own
  right, so `fs.write_bytes` lands now and carries the flag.

**Sandboxing the CLI.** The converter is an arbitrary third-party binary, so containment is
by construction, not by trust:

1. A fresh `tempfile::TempDir` per call.
2. The input bytes are written **inside** it under the original file name (extension
   preserved, name sanitized to a single path segment).
3. The child process runs with `current_dir(tempdir)` and the document argument passed as a
   **relative** name (`{document}` expands to `./toto.pptx`), so a tool that writes beside
   its input (as `doc-convert` does, it creates `toto_docling/`) writes inside the tempdir.
4. `TMPDIR`, `TMP`, `TEMP` are pointed at the tempdir; `env_clear()` is NOT used, because a
   converter legitimately needs `HOME`, `PATH` and model caches.
5. The command is an argv **list**, never a shell string: no redirection, no `&&`, no glob.
   A user who wants hard OS-level containment supplies their own wrapper as argv[0]
   (`sandbox-exec`, `bwrap`, `docker run`); this is documented.
6. Result read from stdout only; the `-o`/output flags are never injected. stderr is
   captured, capped, and only logged on failure (`doc-convert` writes progress bars there).
7. The tempdir is dropped on every path, including timeout: on timeout the child is killed
   (`Child::kill`) and awaited before removal, so no process is left writing into a
   directory being deleted.
8. A test asserts that after a real `doc-convert` run the tempdir is gone and that the
   `_docling` leftovers were created inside it, never next to the server's cwd.

**Failure semantics.** Extension eligibility is validated **before** any byte is written, so
an ineligible extension with the flag set fails with `ERR_NOT_SUPPORTED` and stores nothing.
Once the source bytes are committed, a conversion failure does NOT roll back the upload and
does NOT fail the call: the response carries `documentation: {"error": {"code": ..., "message": ...}}`.
Deleting the user's just-uploaded file because a third-party converter crashed is worse than
returning a file without its companion, and `fs.documentize` exists to retry.

## Changes

### `crates/mcp-fs/src/config.rs`

New secret newtype mirroring `Dsn` exactly (transparent serde, `Debug` -> `Secret(redacted)`,
`Display` -> `redacted`, single `expose()`):

```rust
pub struct Secret(String);
```

New section, added as `pub doc_service: DocServiceConfig` on `ServerConfig`:

```yaml
doc_service:
  enabled: false                 # off by default, nothing changes for existing deployments
  mode: cli                      # cli | api
  extensions: []                 # empty = the built-in eligible set
  max_input_bytes: 536870912     # 512 MiB, refuse to convert beyond this
  cli:
    command: ["doc-convert", "--stdout", "--quiet", "{document}"]
    timeout_secs: 900
  api:
    url: ""
    auth_header: Authorization   # header NAME, not necessarily a bearer
    auth_token: ""               # secret, inject with ${VAR}
    response_field: ""           # empty = response body IS the markdown
    timeout_secs: 900
```

Boot validation in `ServerConfig::validate()`:
- `enabled` + `mode: cli` requires a non-empty `cli.command` whose argv contains exactly one
  `{document}` placeholder;
- `enabled` + `mode: api` requires a non-empty `api.url` starting with `http://`/`https://`,
  and a non-empty `api.auth_header` when `api.auth_token` is set;
- unknown `mode` is rejected with the list of accepted values.

### `crates/mcp-fs/src/docs/service.rs` (new)

```rust
#[async_trait]
pub trait DocService: Send + Sync {
    /// Convert `bytes` (a document named `file_name`) to Markdown. Stateless.
    async fn to_markdown(&self, bytes: &[u8], file_name: &str) -> Result<String>;
}

pub fn eligible(path: &str) -> bool;              // extension gate
pub const DOC_SERVICE_EXTS: &[&str] = &[
    ".pptx", ".pptm", ".potx", ".ppsx", ".ppt",   // PowerPoint
    ".docx", ".doc",                              // Word
    ".pdf",                                       // PDF
    ".mp3", ".m4a", ".wav", ".ogg", ".flac", ".aac", ".opus", ".wma",   // audio
    ".mp4", ".mov", ".mkv", ".webm", ".avi", ".m4v", ".mpeg", ".mpg",   // video
];

pub fn from_config(cfg: &DocServiceConfig) -> Result<Option<Arc<dyn DocService>>>;
```

- `CliDocService`: tempdir + argv + `tokio::process::Command`, per the sandbox rules above.
  Non-zero exit or empty stdout -> `ERR_INTERNAL` with exit code and capped stderr tail.
  Timeout -> `ERR_INTERNAL` `"doc service timed out after {n}s"`.
- `ApiDocService`: one `reqwest::Client` built at boot with the configured timeout.
  Request: `POST {url}`, `multipart/form-data`, part `file` (filename = original name,
  content-type from `docs::mime::guess`, falling back to `application/octet-stream`).
  Auth: `headers.insert(auth_header, auth_token.expose())` when the token is non-empty.
  Response: 2xx, body is the Markdown; if `response_field` is set, the body is parsed as JSON
  and that field is read. Non-2xx -> `ERR_INTERNAL` with status + capped body.
  This contract is ours on both ends; `scripts/doc_service_fake.py` implements it.

Built once at boot (unlike the OCR provider, which is rebuilt per call) so the HTTP client
and its connection pool are reused, and so tests can inject a stub without touching config.

### `crates/mcp-fs/src/core/fs_ops.rs`

One new engine function, the only place the feature is implemented:

```rust
/// Store raw bytes, optionally generating the Markdown companion through the
/// configured document service. Keys: `path`, `bytes_written`, `overwritten`,
/// `documentation` (null when not requested).
#[allow(clippy::too_many_arguments)]
pub async fn write_bytes_documented(
    client: &VolumeClient,
    safety: &SafetyManager,
    doc: Option<&dyn DocService>,
    person: &str,
    mount_id: &str,
    norm: &str,
    data: &[u8],
    overwrite: bool,
    create_parents: bool,
    documentation: bool,
) -> Result<Value>;

/// Run the document service on a file already stored in the volume and write its
/// companion. Keys: `path`, `md_path`, `bytes_written`, `overwritten`.
pub async fn documentize(
    client: &VolumeClient,
    safety: &SafetyManager,
    doc: Option<&dyn DocService>,
    person: &str,
    mount_id: &str,
    norm: &str,
    overwrite: bool,
) -> Result<Value>;
```

Order of operations in `write_bytes_documented`:
1. if `documentation`: service configured? else `ERR_NOT_SUPPORTED`
   (`"document service is not configured"`); `eligible(norm)`? else `ERR_NOT_SUPPORTED`
   with the accepted extension list; `data.len() <= max_input_bytes`? else
   `ERR_INVALID_ARGUMENT`. **All before writing anything.**
2. `write_bytes(...)` unchanged (quota, audit, no-clobber, read-before-write).
3. if `documentation`: `to_markdown` -> `write_text(companion_md_path(norm), md, overwrite=true, create_parents=true)`;
   the companion is charged and audited like any write (op `doc_service`).
4. `documentation` key = `{"md_path", "bytes_written"}` on success, `{"error": {"code","message"}}`
   on failure, `null` when not requested.

`documentize` reuses steps 1 and 3 against bytes read from the volume, and honours
`overwrite` on the companion (`ERR_NO_CLOBBER` when the companion exists and `overwrite` is
false).

### `crates/mcp-fs/src/tools/write.rs` + `document.rs`

Two new tools (57 total, contract golden regenerated with `MCPFS_REWRITE_TOOL_CONTRACT=1`):

```
fs.write_bytes    Write raw bytes (base64) to a file.
  mount_id* string   Project/volume id the operation targets.
  path*     string   Absolute POSIX path within the volume.
  base64*   string   File content, base64 encoded.
  overwrite bool=false
  create_parents bool=true
  trigger_documentation_service bool=false
      Also generate the Markdown companion (path.md) through the configured
      document service. Supported for PowerPoint, Word, PDF, audio and video only.
  -> {"path", "bytes_written", "overwritten", "documentation"}

fs.documentize    Generate the Markdown companion of a stored document.
  mount_id* string
  path*     string
  overwrite bool=false
  -> {"path", "md_path", "bytes_written", "overwritten"}
```

Invalid base64 -> `ERR_INVALID_ARGUMENT`.

### `crates/mcp-fs/src/api/dataplane.rs` + `openapi.rs`

- `POST /api/fs/{mount_id}/write-bytes` (JSON body, `JSON_BODY_LIMIT`): mirrors
  `fs.write_bytes`.
- `POST /api/fs/{mount_id}/documentize` (JSON body): mirrors `fs.documentize`.
- Existing multipart `POST /api/fs/{mount_id}/upload` gains the text form field
  `trigger_documentation_service` (`"true"`/`"1"` = on, absent/other = off). It applies to
  every file in the form; eligibility of **all** files is validated before the first write,
  so a mixed batch fails cleanly with nothing written. The response gains
  `"documentation": [ ... ]`, one entry per written file, same shape as above.
- Both new routes and the new form field are declared in `openapi.rs` alongside the existing
  ones; the existing spec tests are extended.

## Assumptions and defaults

- **Assumption**: the feature ships disabled (`doc_service.enabled: false`). Every existing
  deployment and every existing test is unaffected; the flag set while disabled returns
  `ERR_NOT_SUPPORTED` rather than silently storing the file without a companion.
- **Assumption**: `.ppt`, `.doc` (legacy binary Office) are listed as eligible. Whether the
  configured converter handles them is the converter's business; `doc-convert` will fail and
  the error is surfaced. `extensions` in config overrides the built-in list, so a deployment
  can narrow it.
- **Assumption**: `.xlsx` and images are NOT eligible. The user named PowerPoint, Word, PDF,
  audio, video; the built-in extractor already covers xlsx/images through `fs.extract_text`.
- **Assumption**: the companion is written with `overwrite=true` on upload (the source was
  just written, an older companion is stale by definition), and with the caller's `overwrite`
  on `fs.documentize`.
- **Assumption**: `{document}` is the only placeholder in the CLI argv. No `{output}`, no
  `{name}`: the contract is stdout.
- **Assumption**: stderr is captured and capped at 8 KiB (tail kept). `doc-convert` writes
  megabytes of progress bars there; it must never reach a log line or an error message whole.
- **Assumption**: `api.auth_header` defaults to `Authorization`, and the token value is sent
  verbatim, so a bearer scheme is expressed as `auth_token: "Bearer ${TOKEN}"`. This is the
  only way to support both bearer and non-bearer headers with one setting.
- **Assumption**: base64 in `fs.write_bytes` is standard base64 with padding, decoded with
  the crate already in the tree (the one `fs.read_bytes` encodes with).

## Test plan and verification

1. `write_bytes_documented` with the flag off: byte-identical result to `write_bytes`, and
   `documentation` is null.
2. Flag on, `.pptx`: source stored, `/toto.md` stored with the stub's Markdown, both charged
   against the quota, two audit entries.
3. Flag on, `.txt` / `.xlsx` / `.png`: `ERR_NOT_SUPPORTED`, **and the file does not exist**
   afterwards (the pre-write validation is what is really under test).
4. Flag on, service not configured: `ERR_NOT_SUPPORTED`, nothing written.
5. Flag on, stub returns an error: source exists, companion does not,
   `documentation.error.code` is set, the call is 200/ok.

## Open risks

- **Latency.** Measured 22 s for a one-page PDF with `doc-convert` on this machine; a video
  will be minutes. A synchronous upload holds an HTTP connection and a tokio task for that
  long. Mitigation: `timeout_secs` defaults to 900 and is documented as the knob; clients
  must set their own read timeout accordingly. If this becomes painful in practice, the
  asynchronous variant is a follow-up, and `fs.documentize` is already the retry surface it
  would need.
- **No hard OS sandbox.** Containment is cwd + relative path + `TMPDIR` + argv-without-shell.
  A converter that writes to an absolute path or to `$HOME` escapes it and our cleanup will
  not catch it. Full containment needs `sandbox-exec`/`bwrap`/a container, which would break
  `doc-convert` (model caches, network) and is therefore left to the operator via the argv
  wrapper. This is stated in `.agent_docs/config.md`, not hidden.
- **Resource exhaustion.** Nothing limits concurrent conversions: N simultaneous uploads
  spawn N converter processes, each of which may load ML models. Deliberately deferred; a
  `max_concurrency` semaphore is the obvious follow-up and is cheap to add later on
  `CliDocService`.
- **Quota accounting.** The companion is charged to the uploader's write quota. A large
  conversion can therefore make a subsequent write fail with `ERR_WRITE_QUOTA_EXCEEDED`.
  That is the correct behaviour (the bytes are real) but it is a visible behaviour change
  for anyone using the flag; documented.
- **Partial batch on multipart upload.** Eligibility is validated for all files up front, but
  a conversion failing on file 3 of 5 still leaves files 1 and 2 with companions and 3
  without. The per-file `documentation` array reports exactly which, and no write is lost.
- **`.doc`/`.ppt` eligibility** is declared but not verified against `doc-convert`, whose
  supported list (observed: `.bmp .docx .jpeg .jpg .pdf .png .potx .ppsx .pptm .pptx .tif
  .tiff .webp .xlsx`) does not include them. The call will fail at the converter and be
  reported; no data is lost.
