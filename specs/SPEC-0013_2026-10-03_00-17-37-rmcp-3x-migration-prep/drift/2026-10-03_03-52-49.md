# Discovered drift: two undeclared error-path deviations found while wiring the transport swap

> Discovered during: US-0008 (transport swap)
> Originating register entry: none (new discovery, not a DDRIFT-001 surplus)

## What happened

US-0008's non-regression list (spec Section 5, the two declared breaks) names only the
`initialize` requirement and the response-framing default. Wiring `rmcp`'s own `StreamableHttpService`
and `ToolRouter::call` dispatch surfaced two more error-path differences, neither declared, both
unavoidable without reimplementing the dispatch the migration exists to delete:

1. **Unknown tool name.** The old hand-rolled transport returned `"Unknown tool: '<name>'"`. `rmcp`'s
   own `ToolRouter::call` hard-codes `"tool not found"` for an unmapped name
   (`rmcp-3.5.0/src/handler/server/router/tool.rs:566,571`). The error **code** is unchanged
   (`INVALID_PARAMS` / `-32602`); only the message text differs. Test:
   `unknown_tool_is_invalid_params` in `app.rs`.
2. **Malformed JSON-RPC body.** The old transport answered with an HTTP 500 and a hand-built JSON
   error object. `rmcp`'s `expect_json` decode step answers HTTP 415 (`Unsupported Media Type`)
   with a plain-text body containing `"deserialize"`, before any JSON-RPC envelope can be formed.
   Test: `malformed_json_is_rejected_at_the_json_rpc_decode_step` in `app.rs`.

A third, lower-stakes corner: `resources/list` (an MCP-spec-defined method this server never
advertises resources for) now gets `rmcp`'s own empty-list default instead of a `-32601`
method-not-found error, because `rmcp` handles spec-defined methods at its own protocol layer
before this server's `ToolRouter` ever sees them. Test:
`a_spec_defined_method_outside_tools_gets_rmcps_own_empty_default`.

## Why these were not pre-declared

Section 5's declared-break analysis (written before any `rmcp` dependency existed in this repo,
per DDRIFT-001) focused on the two biggest, most observable axes (handshake requirement, framing
default) found via documentation research. These three narrower error-path differences only became
visible once the real dispatch was wired and exercised with real requests, which is exactly the
empirical-testing discipline DDRIFT-001 and the two prior drift entries in this run already
established as necessary for this migration.

## Assessment

Low severity: all three are error-path or protocol-corner responses, not changes to any
successful tool call's behavior, name, authorization, or return shape (DR-007 holds for every
`#[tool]` method itself). The error **codes** that matter for programmatic handling
(`INVALID_PARAMS`/`-32602`) are preserved; only human-readable message text and, for malformed
input, the HTTP status code, differ. No known in-repo consumer branches on the exact old message
text or the old 500 status for a malformed body (the one in-repo consumer, `crates/agent`, was
updated in the same change, DR-010).

## Not a spec edit

Per Invariant 6 / Section D, `spec.md`'s Section 5 declared-break list is not amended here. This
drift file is the record; it is surfaced to the user at Phase 6.5 of this implementation run
rather than silently absorbed as if it were already covered by DR-006/DR-007's exclusions.
