# Discovered drift: DR-009/DT-001/DT-003's exact wire shapes are unreachable under the
corrected session-manager config

> Discovered during: US-0008 (transport swap)
> Originating register entry: DDRIFT-001 (via the 2026-10-03_00-38-28.md correction)

## What happened

The 2026-10-03_00-38-28.md correction settled on `LocalSessionManager` +
`legacy_session_mode: true` to restore the mandatory-`initialize` behavior DR-009 wants, in place
of the spec's originally planned `NeverSessionManager` + `legacy_session_mode: false`.

US-0008's implementer empirically tested this corrected pairing against a real HTTP request
(`tower::ServiceExt::oneshot`, not just source reading) and found it does not produce the literal
shapes DR-009/DT-001/DT-003 specify:

- **DT-001** (missing `initialize` → JSON-RPC error, `code == -32600`, message containing
  `"initialize"`): the real response is `HTTP 422`, plain-text body
  `"Unexpected message, expect initialize request"` (rmcp 3.5.0,
  `transport/streamable_http_server/tower.rs:2109-2163` and `server_side_http.rs:198`). Never a
  JSON-RPC error object, never code `-32600`. This path is unconditional in rmcp's source; no
  configuration reaches around it.
- **DT-003** (JSON `Content-Type` once initialized): with `legacy_session_mode: true`, every
  request on an established session is dispatched through `create_stream` → SSE, unconditionally.
  `StreamableHttpServerConfig::json_response` is only consulted on the stateless branch, which is
  unreachable once `legacy_session_mode: true` is set. Real result: `text/event-stream`, SSE-framed,
  same as before the migration.

In rmcp 3.5.0's actual source, no session-manager/legacy-mode pairing satisfies "initialize
mandatory" + "JSON-RPC `-32600` rejection shape" + "JSON default framing" simultaneously; the
mandatory-initialize path and the JSON-default-framing path are mutually exclusive branches
selected by the same flag.

## Decision

User decided (2026-10-03, this run): **keep `LocalSessionManager` + `legacy_session_mode: true`**
(mandatory `initialize` preserved as real behavior), and **relax DT-001 and DT-003 to match rmcp's
actual, verified shapes** rather than chase the spec's originally imagined exact envelope:

- **DT-001 (corrected)**: a bare `tools/call`/`tools/list` with no prior `initialize` on a fresh
  connection SHALL receive a `4xx` HTTP response whose body contains the substring `"initialize"`
  — verified against the real shape (`HTTP 422`, text body `"Unexpected message, expect initialize
  request"`), not a JSON-RPC `-32600` envelope.
- **DT-003 (corrected)**: once a session is established (post-`initialize`), the response
  `Content-Type` for a plain tool call is `text/event-stream` (SSE), matching the pre-migration
  behavior on this specific axis — this is NOT the break originally declared in Section 4 row 2;
  that row's "JSON becomes the default" claim does not hold under the session-manager config that
  actually produces mandatory `initialize`. The framing break stands only in Section 4 row 2's
  general sense (rmcp's streamable-HTTP mode exists and could do JSON framing under a different,
  incompatible configuration), not as this migration's own shipped, observable behavior.

## Scope of the correction

DR-009 and Section 4 row 1/row 2 of the spec's compatibility table are corrected in effect (not in
the spec file, per Invariant 6) to: `initialize` IS mandatory (DR-008/DR-009's core intent
preserved); the rejection shape is whatever rmcp 3.5.0 actually emits for it (4xx + "initialize"
substring, not a hand-crafted -32600 JSON-RPC body); the response framing for an established
session remains SSE, which means the "JSON becomes default" break from Section 4 row 2 does NOT
materialize in this migration's actual shipped behavior. DR-010 (agent client performs
`initialize`) stands unchanged — it is still required now, confirmed necessary by this very
investigation.

## Not a spec edit

Per Invariant 6 / Section D, `spec.md` is not modified. This drift file and
`2026-10-03_00-38-28.md` together are the authoritative record of what the migration actually
ships on this axis; US-0008's tests are written against the shapes recorded here, and this file's
summary is carried into the final report (Phase 6.5).
