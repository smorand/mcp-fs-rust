# Discovered drift: Section 2.3's "internal, free to remove" claim about ToolRegistry/ToolSchema
is false — deletion blast radius is ~20 files, not 4

> Discovered during: US-0009 (delete old mcp layer + final gate)
> Originating register entry: none (new discovery)

## What the spec claims

Section 2.3 ("Contracts touched"): "`ToolRegistry`/`ToolSchema`/`Args`/`ToolHandler` are called
only from `crates/core/src/tools/*.rs` and `crates/core/src/app.rs`, all within this codebase.
Free to rename or remove; no compatibility plan owed." DR-003 accordingly scopes this story to
deleting 4 files (`mcp/{mod,registry,schema,args}.rs`) and removing 16 pinning tests.

## What was actually found

`ToolRegistry`/`ToolSchema`/`Args`/`ToolCtx` are referenced across essentially every file under
`crates/core/src/tools/` (fs families, admin, git, git_auth, git_pr, web, context7, sqlite, db,
doc, search, search_semantic — grep counts ranged 5 to dozens per file), not only the git family
US-0005/US-0006's own drift note anticipated. Three load-bearing consumers make this non-dead code:

1. **`crates/core/src/app.rs:103`**: `crate::tools::register_all(&mut registry, &features,
   &config)` runs at boot and populates `AppState.registry: Arc<ToolRegistry>` for every tool
   family, not only the MCP-facing ones.
2. **`crates/core/src/api/openapi.rs:124`** (`catalog()`): reads `state.registry.list_payload()`
   as the single source of truth for `/api/swagger.json`'s REST endpoint descriptions and
   parameters. This is a live, currently-serving production code path entirely independent of the
   MCP transport this spec migrates — the spec's Section 2 perimeter never mentions
   `api/openapi.rs` at all.
3. Per-family `register()`/`register_with()` implementations in files the project's own
   architecture doc describes as "already migrated to `core::fs_ops`" (e.g. `read.rs`, `write.rs`,
   `edit.rs`, `listing.rs`, `metadata.rs`, `lifecycle.rs`, `document.rs`, `search.rs`,
   `search_semantic.rs`) still carry a live, separately-tested `ToolSchema`/`ToolRegistry`-based
   registration path, with roughly 700 tests across the tool-family files built against it
   (`git.rs` alone: 526; `git_auth.rs`: +70; plus the ~158 across the fs-family files) — none of
   which have an equivalent test against the new `#[tool]`-based `McpServer` surface.

`web.*`, `context7.*`, `sqlite.*`, `db.*`, `doc.*` tool families are registered into the old
`ToolRegistry` but are NOT part of the 94-tool golden contract and are not reachable via the new
`/mcp` route (which only mounts the rmcp `McpServer`) — their fate (delete, or migrate separately)
is undecided and outside this spec's stated 94-tool scope.

## Why this blocks DR-003 as scoped

Deleting `mcp/{mod,registry,schema,args}.rs` today would either: (a) break the boot-time
`register_all` call and the `/api/swagger.json` REST documentation plane, a regression DR-006
forbids since that plane is not a declared break; or (b) require silently dropping ~700 tests with
no replacement coverage, which neither DR-003 nor any invariant in this workflow permits.

## Required resolution (not performed here, pending a decision)

A per-family refactor substantially larger than this story's stated scope (~4 files, ~860 lines):
extract each family's handler bodies into `pub(crate)` functions shared between the old
`register()` path and new `#[tool]` methods (the pattern already used for `fs.*`/`admin.*`/
`search.*`, and the one this run's own prior drift note prescribed for `git.*`), rewire
`api/openapi.rs`'s catalog onto `McpServer::tool_router().list_all()` (confirmed feasible:
`rmcp::model::Tool` serializes with the same `name`/`description`/`inputSchema` shape
`list_payload()` already produces), remove `AppState.registry`/`register_all`/`EnabledFeatures`
from `app.rs`, and re-point every family's existing test suite at the new shared functions without
losing coverage. Estimated at ~20 files, ~32,000 lines touched — an order of magnitude beyond
DR-003's stated 4-file scope.

## Not a spec edit

Per Invariant 6 / Section D, `spec.md` Section 2.3 and DR-003 are not corrected here. This drift
file is the record, surfaced to the user at Phase 6.5. No code was changed while making this
discovery (`git status` confirmed clean).
