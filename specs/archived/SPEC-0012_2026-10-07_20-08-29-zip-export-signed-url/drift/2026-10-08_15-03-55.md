# Discovered drift — SPEC-0012, during US-0003 implementation

> Discovered: 2026-10-08, implementing `GET /exports/{token}` (FR-NEW-009, FR-NEW-017)
> Originating register entry: none — this is new, not a surplus against an existing `DRIFT-XXX`
> (the spec's Phase 6 gate shipped `IMPLEMENTABLE`, zero open drift)

## What the spec presupposed

DEC-011 states: "the token alone must resolve it" — i.e. `GET /exports/{token}` needs no `mount_id`
in the URL because the token is sufficient to locate the export record. FR-NEW-009's atomic
delete-and-fetch primitive (built in US-0001) takes only `token` and `now`, with no `volume_id`
parameter, consistent with that assumption.

## What the code actually does

Under the SQLite backend, each project/volume's relational metadata lives in its own database file
(`{meta.dir}/{project}.db` — confirmed at `crates/core/src/storage/mod.rs`'s `StoreManager::client`
resolution). There is no single connection that can see every volume's `export_links` rows at once.
Since the download route has no `mount_id` to pick a connection with, US-0003's implementation
(`crates/core/src/exports.rs`, `claim()`) resolves this by calling `admin.list_all_projects()` and
running the atomic delete-and-fetch primitive against **each project's database in turn** until one
reports success.

- This is correct (no false negative: every volume is tried before concluding 404) but its cost is
  **O(P)** connection attempts per download request, where P is the number of projects on the server,
  not O(1) as DEC-011's "the token alone resolves it" implies.
- Under PostgreSQL/SQL Server (one shared database, `volume_id` is just a column), this loop is
  wasteful but not incorrect: the same connection/pool answers every iteration, so the real cost there
  is closer to O(P) redundant queries against one connection rather than O(P) separate connections.
  SQLite is the affected backend.

## Nature

**Missing capability** (DEC-011 assumed an O(1) token→volume resolution path that was never designed;
nothing was ever false about SQLite's storage model, the spec simply didn't consider it when
concluding "the token alone resolves it").

## Resolution

Not resolved in this lot — the implementer's workaround is correct and shipped (16/16 tests green,
full suite 2128/0 failed). Two possible real fixes, for a future entry:
1. A lightweight global `token -> volume_id` index (its own tiny table, or piggybacking on a
   shared/default-backend connection even under SQLite), giving O(1) resolution.
2. Encode a short volume hint in the token/URL itself (changes the URL shape DEC-011 settled, so this
   would need a new decision, not a silent change).

## Detected by

Nothing automated flags this — it is a scaling characteristic, not a correctness bug. A future
benchmark/load test on a server with many projects would be the signal (currently no such benchmark
exists in this suite).

## Blocks which requirement

None — informational. FR-NEW-009/017 are fully satisfied; this is a cost characteristic, not a
functional gap.
