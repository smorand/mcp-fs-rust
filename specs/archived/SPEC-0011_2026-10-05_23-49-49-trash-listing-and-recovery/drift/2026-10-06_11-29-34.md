# Discovered drift — SPEC-0011_US-0002

> Discovered: 2026-10-06, during SPEC-0011_US-0002 implementation
> Originating registered entry: none — this is a fresh discovery, not a closure of a pre-existing
> `DRIFT-XXX`. The source spec's Implementability Gate (§18) verdict was `IMPLEMENTABLE`, zero
> registered drift.

## What the spec says

`FR-NEW-002` (spec §6): "WHEN `fs.delete` soft-deletes a path ... THE system SHALL insert a
`trash_entries` row ... **in the same transaction as the `rename`**."

NFR 7.4 (spec §7.4): "The `trash_entries` insert/delete happens in the same transaction as the
corresponding `rename` ... a failed rename never leaves an orphaned `trash_entries` row, and a
failed insert never leaves an untracked rename (both roll back together)."

US-0002's own Technical Context instructed: "do not call US-0001's insert method after the rename
has already committed outside a shared transaction."

## What the code does

`VolumeClient::meta` is a trait object (`Arc<dyn MetaBackend>`); `MetaBackend::rename` commits its
own transaction internally (`storage/meta.rs`, the generic `rename` impl, unchanged by this spec).
US-0002's `rename_with_collision_retry` (`crates/core/src/core/fs_ops.rs:1006`) calls
`client.rename(...)` through that trait object, which has already committed by the time it returns.
The new `VolumeClient::trash` handle's `record_trash_entry` (`storage/meta.rs:277-283`) then runs
its own, separate `run_retrying` transaction immediately after. The doc comment on
`record_trash_entry` states this explicitly: *"Runs in its own transaction rather than the rename's
... This is therefore a best-effort companion write immediately after a successful rename, not a
joint commit with it."*

Citations: `crates/core/src/storage/meta.rs:270-276` (doc comment), `crates/core/src/storage/meta.rs:277-314`
(`record_trash_entry`), `crates/core/src/core/fs_ops.rs:1006` (`rename_with_collision_retry`),
`crates/core/src/core/fs_ops.rs:1103` (call site inside `delete_path`).

## Nature

**Bypassed abstraction.** `MetaBackend` is a trait object precisely so `VolumeClient` never needs to
know which dialect it is talking to; that same boundary is what prevents the rename and the trash
insert from sharing one transaction without either widening `MetaBackend` (adding a new
dialect-agnostic method that performs both operations atomically) or giving `VolumeClient` dialect
knowledge it was designed not to have.

## Observable consequence

If the process crashes (or the node is killed, or power is lost) in the narrow window between the
rename's commit and the trash-entry insert's commit, the file is live in the trash directory
(renamed) but has no `trash_entries` row. `fs.trash_list`/`fs.trash_restore` would not see it as a
tracked entry until FR-NEW-011's lazy backfill (US-0004/US-0005) picks it up on next access — which
it will, since the backfill scans untracked nodes directly under `trash_dir`. So the practical
blast radius is bounded: the file is not lost, and the backfill mechanism (built for exactly the
"legacy untracked trash node" case) self-heals this window as a side effect, with a best-effort
`deleted_at` (current time, since no epoch-ms-parseable original cause survives) rather than the
exact original delete time. No acceptance test in the spec's 63-test suite exercises this window;
all 15 of US-0002's own tests pass.

## Resolution during implementation

Not resolved in this lot. A real fix requires one of:
(a) a new `MetaBackend` trait method performing rename + trash-entry insert as one transactional
    unit (dialect-agnostic, implemented once in the generic `impl`), replacing the two-call
    sequence `rename_with_collision_retry` + `record_trash_entry`; or
(b) accepting the current best-effort-sequential write and relying on FR-NEW-011's backfill as the
    de facto self-healing mechanism for the crash window, documenting that explicitly as the
    accepted behavior rather than a defect.

## Decision made

**Decided 2026-10-06 (user, at Phase 4.6 CONVERGE):** accept (b) — the current best-effort-
sequential write ships as documented behavior. The `MetaBackend` retrofit for true joint-
transaction atomicity (option (a)) is tracked for later as `backlog/BL-0011_atomic-trash-entry-write.md`,
not as a story in this spec's loop. This lot closes with the gap accepted, not resolved.
