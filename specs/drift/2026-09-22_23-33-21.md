# Discovered drift: git.remote_push reports `remote_sha`, the spec's table says `new_sha`

> Discovered during: US-022 implementation (commit 0e2c245)
> Nature: wire-shape disagreement between the specification and shipped code
> Severity: LOW. Contained, visible, and cheap to settle either way.

## The disagreement

FR-NEW-199's response table lists `git.remote_push` as returning
`branch, remote, remote_branch, created, up_to_date, forced, overwritten_sha, new_sha`.

The shipped tool returns `remote_sha` in that position, not `new_sha`. `remote_sha` is the
key the tool already used before this specification, and three existing tests assert the
response by full equality.

## Why the implementer kept `remote_sha`

Renaming it would have broken shipped assertions that this story was explicitly forbidden
from weakening, for a key whose meaning is identical. The implementer chose continuity and
disclosed the deviation rather than silently satisfying the table.

## Related, same story

The story file contradicted itself on `overwritten_sha` for a forced CREATE: one test asked
for `null`, another for the 40-zero sha. The implementer shipped the zeros and wrote both
assertions accordingly. That one is settled in code; it is recorded here only so the
specification can be corrected if it is ever revised.

## Decision needed from the user

Pick one:
1. Accept `remote_sha` and correct FR-NEW-199's table if the specification is ever revised.
   Cheapest, and the key name carries the same meaning.
2. Rename to `new_sha` for consistency with every other tool in the table, and update the
   three existing full-equality assertions in the same change.

Recommendation: option 1. The table's value is that every tool's key set is pinned SOMEWHERE
authoritative; `remote_sha` is pinned by the frozen tool contract and by tests. Renaming a
shipped key to match a document is churn, not correctness.


## Resolution (orchestrator, post-audit)

**RESOLVED, and the finding was understated.** The user approved settling FR-NEW-199.

Resolved in two parts, because verification against the source showed the disagreement was
wider than a rename:

1. **Spec amended** to accept `remote_sha` over `new_sha`: the name states whose sha it is and
   pairs with `overwritten_sha`. `new_sha` stays correct for the four local-history tools
   (`branch_reset`, `cherry_pick`, `reset`, `revert`), where the sha is newly created rather
   than observed on a remote. The `auth` key was verified inert (one of five fixed class
   literals, never credential-derived, proved by `e2e_new_903`) and recorded in the table.
2. **Code fixed**: the `remote` key was NEVER emitted, which neither this entry nor the converge
   audit caught; both framed the gap as a naming disagreement. Since US-021/FR-MOD-101 gave
   `git.remote_push` a `remote` parameter, a caller pushing to `upstream` got a response that
   never said which remote was pushed to. Now emitted unconditionally, since it always has a
   value (`origin` by default), unlike the genuinely inapplicable `remote_branch` and
   `overwritten_sha`. Commit `aec67cd`.

Verified: the amended spec row and the emitted key set are now an exact nine-key match,
checked by extracting both mechanically rather than by reading.
