# Discovered drift: resuming a conflicted stash creates a merge commit

> Discovered during: US-012 implementation (commit below)
> Nature: gap in the specification, not an implementation defect
> Severity: MEDIUM. It ships wrong behaviour if left unfixed.

## What the specification says

FR-NEW-126: a stash application that conflicts returns the shared conflict response,
applies nothing, records an in-progress operation, and RETAINS the stash entry.
FR-NEW-241: a paused `stash_apply` / `stash_pop` is completed by `git.merge_resolve` and
`git.merge_abort`, "because applying a stash is a merge against HEAD".

Both hold, and both are implemented.

## What the specification never says

What `git.merge_resolve` should DO when the operation it is completing is a stash rather
than a merge. It currently does what it does for a merge: creates a commit and moves the
branch.

That is wrong for a stash. Applying a stash restores uncommitted work to the working tree;
it does not commit anything and does not move the branch. A caller who stashes, switches
branch, pops into a conflict and resolves it ends up with an unexpected commit on their
branch instead of restored working-tree content.

## Why no gate caught it

No FR describes the resumed-success path for a stash, so no acceptance test exercises it.
The conflict is surfaced correctly, the entry is correctly retained, and every written test
passes. The defect lives exactly in the space the specification left blank.

## Two readings, which is why this is not an implementer's call

1. `git.merge_resolve` branches on `op_type`: for `stash_apply` / `stash_pop` it writes the
   resolved tree to the volume, drops the entry only for a pop, and creates NO commit and
   moves NO ref.
2. Stash conflicts get their own completion pair (`git.stash_resolve` / `git.stash_abort`),
   contradicting FR-NEW-241, which deliberately routes them to the merge tools.

Reading 1 is almost certainly intended: FR-NEW-241's rationale is that a stash apply IS a
merge against HEAD, which speaks to the merge ALGORITHM, not to committing the result.

## Recommendation

Adopt reading 1 as a follow-up task in this lot, before the branch merges. It is a small,
contained change to the completion path plus one test asserting that a resumed stash leaves
the branch tip unmoved and creates no commit.

Flagged for user decision rather than implemented, because choosing between the two readings
changes observable behaviour and the specification is silent.


## Resolution (orchestrator, post-audit)

**RESOLVED in code**, user approved the fix rather than shipping the defect.

`merge_resolve` now branches on `row.op_type` through a two-variant `Completion` enum
(`crates/mcp-fs/src/tools/git.rs:4698`): `MergeCommit` keeps the previous behaviour, and
`WorkingTree { drop_stash }` completes a stash without creating a commit or moving any ref.
A resolved apply keeps its stash entry (FR-NEW-131); a resolved pop drops it, which is where
the conflicted pop's deferred delete belongs, since resolution is the point the work lands.
`ResolveResponse` is unchanged: `status` becomes `"applied"`, the literal the non conflicting
stash tools already return, and `merge_commit` is `None` rather than a fabricated sha.

Proof: three new tests assert the branch tip is byte-identical across a resolved apply and pop,
the commit count is unchanged, and the resolved bytes are in the volume; a fourth,
`a_resolved_merge_still_commits_and_moves_the_branch`, guards the merge path and passed both
before and after the change. No existing test encoded the buggy behaviour, so none was edited.
Commit `a148421`.
